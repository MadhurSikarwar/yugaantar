Unique selling proposition

When a device is lost, operators need to cut it off everywhere and later prove what happened. In our service every allow, deny and alert is logged with the rule and the events behind it, and anyone holding a pinned checkpoint and the public key can verify that the log up to that point has not been altered. Revocation reaches every honest node within a stated, measured bound, and a node that cannot get fresh revocation data locks itself instead of guessing. Our own signed logs feed an explainable rules-based detector, and every limit is written down.

Architecture

caller ─JSON─▶ track4_service.py ─▶ validate_in ─▶ policy (owner / disabled / revoked) ─▶ reply
                 │ new process per request    store: locked, atomic, HMAC-tagged state
                 │                            audit: SHA-256 hash chain + ML-DSA-65 checkpoints
                 └ protected_read: ML-KEM-768 encapsulation, proof = HMAC-SHA256(secret, challenge‖body)
authority ─signed revocation lists via untrusted courier─▶ node A, B, C   (deny all if list older than T)
device ─ML-DSA-65 signed request─▶ node: signature, node binding, owner, key version, window, nonce, policy
operator: verify-log (pinned head + key) · explain · detector over our own verified logs · backup/restore
  • Identity and authorization. The judged adapter enforces permissions on the stated actor. The contract carries no credential, so it does not authenticate callers. Device identity is verified in the node layer by ML-DSA-65 signatures.
  • Keys. These are generated at runtime and never stored in the repository. The adapter's audit key and the authority and device keys are ML-DSA-65. Key rotation is journalled (PREPARED, then COMMITTED) with activation time C more than T + s ahead and no grace period. Backups are HMAC-authenticated.
  • Libraries. pqcrypto==0.4.0 (ML-KEM-768, ML-DSA-65) and the Python standard library (HMAC, SHA-256). No custom crypto, no ML.
  • Working: all five operations, the node layer, rotation, backup, signed logs, the detector, the red-team suite and the simulation. Not built: encrypted messaging (goals 9 to 12).

One-page threat model

Assets

File bodies (confidentiality). Owners, revocations and grants (integrity, and no rollback once acknowledged). Audit logs (tamper evidence). Signing and state keys (secrecy). Service availability for legitimate owners.

Adversaries

  • An unauthorized caller who can send any JSON and claim any actor.
  • Whoever holds a lost or stolen device and its key.
  • A network or courier that delays, drops, replays or alters messages.
  • A log injector who uses hostile identifier text.
  • A local attacker with write access to a state directory.

Trust boundaries

BoundaryWhat is checked
Caller → adapterPermission only: owner, not disabled, not revoked. The identity is claimed, not proven.
Device → nodeML-DSA signature, node binding, owner = actor, active key version, time window, single-use nonce, then policy
Authority → nodeSigned, numbered list. Older or forged lists are rejected. If the list is older than T, the node denies all.
Process → diskHMAC-tagged state, atomic writes, hash-chained signed logs. The keys share the directory.
Operator → outsideA pinned log head and public key, kept outside the directory

Assumptions

The adapter's caller states the true actor. Node clocks are within s = 2 s. The authority and nodes are not compromised. pqcrypto is correct. Pins are stored elsewhere.

Defenses (each tested; see the evidence sheet)

  • Deny by default, with a uniform deny response. Revocation is persisted before the reply, and peers are unaffected.
  • Strict input checks give a generic error and no traceback.
  • Revocation is enforced on every honest node by r + T + s. Stale nodes lock.
  • Replayed, misdirected and forged requests and lists are rejected.
  • Rotation and restore recover from a crash at every step, and revoked keys are never restored.
  • Edits, deletions, reordering and truncation before a pinned head are detected, along with the first bad entry. Hostile text cannot forge entries.
  • Our own logs are verified before the detector runs. Unverified requests are never attributed to the named actor.

Exclusions and remaining risks

  • No caller authentication in the adapter. Anyone can claim any actor.
  • Whoever can write a directory can read its signing key and rebuild its log. A pin exposes this only up to the pinned entry. Entries after the newest checkpoint or pin can be cut unnoticed. A full rollback of a state directory is not detectable locally.
  • Open review findings: long identifiers can grow the state file until every call fails (high, open). The authority does not authenticate its operator, including for rotation. Backups are not encrypted, and a restore loses newer enrolments and grants.
  • No transport encryption and no forward secrecy (goals 9 to 12 are not supported). A reused protected_read challenge is accepted.
  • The detector is measured only on synthetic data: 22 practice rows cannot establish accuracy, and the held-out set reflects our own assumptions. Not yet run on Linux.

Largest remaining risk: the adapter cannot tell who is calling. Strong identity exists only where devices sign their requests.
